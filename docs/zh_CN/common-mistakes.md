# 常见错误（Bad → Good）

> 每条错误都来自真实使用场景。看懂了这里，你就知道每个模板为什么要那么写。

## 1. 智能体 写得太全能

**Bad**

```text
你是一个全能的软件开发专家。
你需要分析需求、设计架构、写代码、测试、评审，
并确保最终任务完成。
```

**Good**

```text
你负责实现已经确认的技术方案。
你不负责修改产品需求，也不负责最终 评审。
```

为什么：全能 智能体 同时占用了 智能体 / Squad / Skill / Issue 四个位置，换任务就全部失效；窄 智能体 可以原样复用到下一个任务。

## 2. 小队只有一句空话

**Bad**

```text
大家协作完成任务，必要时互相帮助。
```

**Good**

```text
前端实现 → 前端开发专家（范围含前端）
后端实现 + API 契约 → 后台开发专家（范围含后端）
判门 → 通用小队负责人用 `multica-verification` skill 复跑
业务评审 → 业务评审
测试 → 测试专家

判门 FAIL → 对应实现者
Test FAIL → 对应实现者
```

为什么：小队的价值就是**明确的路由**。路由模糊时，每个智能体都靠猜决定自己下一步做什么。

## 3. Issue 没有验收标准

**Bad**

```text
帮我把这个功能做了。
```

**Good**

```text
目标：...
范围：...
非目标：...
验收标准：- [ ] ...
约束：...
验证方式：...
```

为什么：没有可测试的验收标准，门禁体系（G0–G4）直接失效，验证无处判门。

## 4. 让完成者自证

**Bad**

```text
实现者写完代码后：请自己 评审 一遍，确认没问题后标记完成。
```

**Good**

```text
实现者写完代码后：提供证据（变更文件 + 命令输出），由 对应小队负责人 用 multica-verification skill 复跑判门。
```

为什么：作者会本能地为自己找理由。判门必须由非产出者执行（对应小队负责人复跑或 CI），产出者自证不算数。

## 5. 把硬约束写进提示词

**Bad**

```text
智能体 必须确保代码没有任何安全问题，并且测试全部通过后才能提交。
```

**Good**

```text
用 CI 强制测试通过，用分支保护要求 PR 审批。智能体 指令只是引导。
```

为什么：LLM 指令不是安全边界。真正「必须」的规则要放在工程系统里强制执行。

## 6. 用「做完了」代替证据

**Bad**

```text
通用小队负责人判断任务完成的标准：成员报告完成。
```

**Good**

```text
通用小队负责人判断任务完成的标准：变更文件 + 实际命令输出 + 与验收标准逐条对照。
```

为什么：「完成」是口头声明，证据是可复现的事实。只信后者。

## 7. 无脑复制五 智能体 流程

**Bad**

```text
所有任务都走：技术架构师 → 前端开发专家 / 后台开发专家 → 测试专家 → 对应小队负责人判门。
包括改一行配置、修一个 typo。
```

**Good**

```text
按任务类型选最小组合：Bug 用 bug-fix（跳过 技术架构师），
小改动可以只派 后台开发专家 + 业务评审，研究类任务甚至不需要开发角色。
```

为什么：最佳实践不是固定流程，而是**针对任务选最小可行组合**。流程越重，上下文损耗越大。

## 8. 让对应小队负责人亲自干活

**Bad**

```text
对应小队负责人是万能兜底：其他人做不了的，对应小队负责人自己上。
```

**Good**

```text
对应小队负责人只做路由、门禁判断与升级。实现永远派给对应成员。
```

为什么：对应小队负责人是指挥，哪有指挥亲自干活的。

## 9. 静默把范围内的产物当「不需要」跳过

**Bad**

```text
通用小队负责人：设计这块这次就不做了吧，直接进开发。
（没有标注理由，也没有确认）
```

**Good**

```text
通用小队负责人：设计判定为 N/A，理由是该改动复用现有导出中间件、无新架构决策；
已确认，记录为 N/A，下游门禁按「无设计」分支走。
```

为什么：范围内的产物若判断不适用，必须显式标注 N/A + 理由 + 对应小队负责人确认，否则等于悄悄改了范围。未确认的 N/A 视为范围缺失，应回写 Issue。同样的道理，某一产物被修改后，下游门禁要立即失效重判，不能沿用旧 PASS；同一产物判门连续 3 次 FAIL 就升级人类，别陷入无限返工。

---

## 诊断清单

如果你的小队「看起来在跑，但结果不稳定」，按顺序检查：

1. Issue 有没有可测试的验收标准？（没有 → 一切免谈）
2. 每个 智能体 是不是只干一件事？（有重叠 → 行为会漂移）
3. 判门是不是由非产出者执行？（作者自判 → 等于没查）
4. 完成标准是不是证据？（口头报告 → 无法复盘）
5. 硬约束在不在 CI / 分支保护里？（只在提示词里 → 早晚被绕过）
6. 范围内的产物被判定 N/A 时有没有标注理由并由对应小队负责人确认？（静默跳过 → 等于偷改范围）
7. 上游产物修改后下游门禁是否失效重判？（沿用旧 PASS → 门禁形同虚设）
8. 同一产物反复 FAIL 有没有升级人类？（无限返工 → 消耗而不收敛）
