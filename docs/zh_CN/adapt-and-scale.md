# 裁剪与扩展

> 先跑起来，再调整。不要把第一天花在「设计完美配置」上。

## 什么时候用小队，什么时候直接派给智能体

| 场景 | 做法 |
| --- | --- |
| 单步小任务（改 typo、加一行配置） | 直接派给一个智能体，不需要小队 |
| 多阶段任务（设计 → 实现 → 审查 → 测试） | 用小队 + 启动模板 |
| 紧急生产故障 | `bug-fix` 启动模板 |
| 研究 / 技术调研 | 参考 technical-research（见下文） |
| 只需要产品功能设计与评审 | `product-design` 启动模板，按需组合产品 / UI / 技术可行性 |
| 只需要完成开发阶段 | `development` 启动模板，由研发总监按复杂度动态编排 |

原则：**单个智能体能做的，不要上小队。** 小队的价值是跨阶段协调，不是越多越好。

## 产品设计小队的动态编排与评审

`templates/zh_CN/squad/product-design` 把 产品经理 作为所有需求的第一站，由 产品总监 统一评审；涉及页面或交互时按需加入 UI/UE设计师，涉及跨系统、数据、权限或高成本约束时按需加入 技术架构师。

```text
L1 产品定义 → 产品总监 + 产品经理
L2 体验设计 → L1 + UI/UE设计师
L3 复杂产品 → L1 + 按需 UI/UE设计师 和 / 或 技术架构师
```

产品经理 完成后由 产品总监 判断是否需要 UI/UE设计师 / 技术架构师；需要则继续派发，不做中间正式评审。所有需要的产物完成后，再由 产品总监 使用 `multica-verification` 做一次最终统一评审；完成人类确认后，把产品定义包交给 `development` 或完整 `software-development` 启动模板。

## 开发小队的动态编排

`templates/zh_CN/squad/development` 是一个只覆盖开发阶段的独立小队。它复用现有的研发总监、技术架构师、前端开发专家和后台开发专家，不把四个角色当成每次都必须同时启动的固定班底。

研发总监在 T0 读取 Issue 和现有代码后判断复杂度：

```text
L1 简单 → 研发总监 + 一个相关工程师
L2 中等 → 研发总监 + 相关工程师，技术架构师按需加入
L3 高风险 → 研发总监 + 技术架构师 + 相关工程师
```

开发交接完成后，可以把交接包交给测试小队或部署运维小队。需要完整的设计、实现、测试、部署链路时，继续使用 `software-development` Starter。

## 从最小组合开始

不是所有任务都需要 4 个智能体。常见的成长路径：

```text
1 智能体   → 直接派活
2 智能体  → 前端开发专家 / 后台开发专家 + 业务评审（实现 + 独立业务评审）
3 个智能体 → 通用小队负责人 + 前端开发专家 / 后台开发专家 + 业务评审（有人判门 + 评审）
4 个智能体 → 通用小队负责人 + 技术架构师 + 前端开发专家 / 后台开发专家 + 业务评审（有设计环节）
5 个智能体 → 完整启动模板（+ 测试专家）
6 个以上智能体 → 前后端同场（前端开发专家 + 后台开发专家并行）
```

每加一个智能体，都要问：**新增的独立判断点，值不值得额外的上下文损耗？**

## 什么时候需要更严的流程

以下场景升级为严格交付流程（逐阶段门禁、证据留档、人工审批）：

- 涉及生产数据 / 线上发布
- 涉及安全
- 多模块、多团队协作
- 无法自动验证正确性的领域

反之，探索型 / 低风险任务应使用轻量流程。

## 模型适配

不同模型的能力差异明显：

- 强推理模型：可以承担通用小队负责人判门与业务评审这类角色，门禁可以更严。
- 弱模型：缩小每个智能体的任务粒度，把步骤写得更明确，必要时增加人类检查点。

先按默认 Starter 跑一个真实任务，再根据失败模式调整，而不是提前为「万一」做准备。

## 用 AI 帮你适配仓库到你的技术栈

如果你不想手工改模板，可以直接复制下面这段到 Multica 或任意 AI：

```text
你是本仓库（multica-best-practices）的适配助手。
请把 templates/zh_CN/squad/software-development 这套模板适配到我的技术栈（
[填入语言 / 框架 / 工具链]），要求：
1. 验证命令替换成我们项目的真实命令（lint / test / build）。
2. 保留 G0–G4 门禁结构，只改验证方式和示例。
3. 不新增角色，不扩大流程。
4. 输出可以直接粘贴到 Multica 的完整配置。
```

## 试点推广清单

从 0 到团队推广时：

1. **先跑一个真实项目**：选一个低风险、边界清晰的 Issue，完整跑完 software-development Starter。
2. **复盘**：记录门禁结论与失败模式，调整模板，而不是一上来就扩流程。
3. **再推广**：稳定后再引入其他启动模板或新增智能体。

## 常见问题（FAQ）

**Q：启动模板里没有产品经理 / 测试专家，够用吗？前端 / 后端呢？**

A：普通功能六个角色已足够。产品经理职责可以用 Issue 模板替代（背景 / 目标 / 非目标），测试职责由 `multica-verification` skill 判门 + 测试专家 + CI 承担。前端 / 后端已经拆分为前端开发专家 / 后台开发专家（前端要对接 UI 设计，后端不接触 UI），且**按 Issue 的「涉及端」范围路由，任意角色可缺失**——无设计 / 无前端 / 无后端都是同一套小队指令的排列组合。

**Q：我可以用自己的小队流程吗？**

A：可以。启动模板的核心价值是「职责边界」和「证据门禁」，流程本身应该随你的项目调整。多实例复用见 [`naming-conventions.md`](./naming-conventions.md)（角色+项目+成员标识）。

**Q：为什么没有 technical-research 启动模板？**

A：研究类任务的最小组合是「研究智能体 → 通用小队负责人判门（`multica-verification` skill）→ 人类」，等有真实需求再补，避免未经实战验证的模板（见 [`ROADMAP.md`](../../ROADMAP.md)）。
