# Issue 模板

> 复制到新 Issue，填写后交给软件开发评审小队。

```markdown
# 功能需求

## Issue 来源（必填，二选一）
<!-- 决定本 Issue 的填写深度。选「外部系统链接」时，仅填下方链接 + 摘要 + 涉及端，其余章节跳到「备注」引用 KEY 即可；全量需求在 Jira/Tapd 等系统中，小队按 KEY 拉取 -->
- [ ] 外部系统链接（轻量）：仅填「链接 / 一句话摘要 / 涉及端」，其余章节省略
      - 链接：<ISSUE_URL>
      - 摘要：<!-- 一句话说明要做什么 -->
- [ ] 全量自包含（默认）：本 Issue 即为需求，完整填写以下所有章节

## 背景
<!-- 为什么做这件事？ -->

## 目标
<!-- 这个功能要解决什么问题？ -->

## 范围
<!-- 通用小队负责人按此路由：缺失的端不派角色，对应产物直接跳过 -->
- 涉及端（勾选）：
  - [ ] 设计（需要 技术架构师 出方案）
  - [ ] 前端（需要 前端开发专家）
  - [ ] 后端（需要 后台开发专家 + API 契约）
- 改动内容：<!-- 应该改什么？ -->

## 非目标
<!-- 明确不做哪些事？ -->

## 验收标准（必须可测试）
- [ ]
- [ ]
- [ ]

## 参考资料
<!-- 文档、Issue、截图、代码位置 -->

## 备注
<!-- 其他小队需要知道的信息 -->
```

---

## 为什么这么写

- **范围里的「涉及端」是路由输入**：通用小队负责人的 G0 靠它决定派哪些角色。范围缺失或含糊 → G0 FAIL，而不是通用小队负责人猜。
- **目标 / 范围 / 非目标**三段分离：防止 智能体 自由发挥扩大范围。
- **验收标准必须可测试**：没有可测试的验收标准，判门无法执行（multica-verification skill 无从对照），整个门禁体系会失效。本启动模板 在此之上还增加了专属评审员 的专业评审，但评审同样依赖清晰、可测的验收标准作为基准。
- **「来源二选一」给链接型 Issue 减负**：源头是外部 Issue 系统时，全量需求在外部系统，本 Issue 只需「链接 + 涉及端 + 一句话摘要」即可驱动 G0 路由与门禁；选「全量自包含」时优先填背景/目标/范围/非目标/验收标准，参考资料/备注按需补。两种形态共用同一个 `<ISSUE-KEY>`，门禁体系不变。
- **Issue 是需求契约，不是实现蓝图**：提 Issue 的人通常是产品经理（一个 Issue 即一个需求）。模板只保留需求要素（为什么做 / 做什么 / 涉及端 / 非目标 / 可测试验收标准），技术上下文、约束、追踪矩阵、验证方式、Git 分支等工程产物由小队在运行中产出，不前置成产品经理负担。

## 常见失败

- 只写「帮我把这个功能做了」→ 小队要么瞎猜，要么卡在 G0。
- 不勾选「涉及端」→ 通用小队负责人不知道要不要派前端开发专家 / 后台开发专家，流程会按默认全栈跑。
- 把需求细节写进 智能体 提示词 而不是 Issue → 换一个任务这些指令就失效了。
