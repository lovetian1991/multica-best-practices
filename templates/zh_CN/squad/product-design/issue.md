# Issue 模板

> 复制到新 Issue，填写后交给产品设计小队。

```markdown
# 产品功能设计

## Issue 来源（必填，二选一）
- [ ] 外部系统链接（轻量）
      - 链接：<ISSUE_URL>
      - 摘要：<!-- 一句话说明产品问题或机会 -->
- [ ] 全量自包含（默认）

## 背景
<!-- 为什么现在要处理这件事？已有产品或流程是什么样？ -->

## 目标用户
<!-- 谁遇到了问题？不同角色是否有不同权限或目标？ -->

## 问题 / 机会
<!-- 描述需要解决的问题，不要只写预设方案。 -->

## 期望结果
<!-- 成功后用户或业务发生什么可观察变化？ -->

## 已知范围
- 包含：
- 不包含：

## 成功指标或验收信号
<!-- 可以是业务指标、用户行为变化或可检查的产品结果。 -->
- 

## 已知约束
<!-- 时间、合规、数据、权限、平台、品牌、兼容性等。 -->

## 现有资料
<!-- 现有页面、PRD、用户反馈、数据、竞品或外部链接。 -->

## 已知待确认项
<!-- 不确定就明确写出，不要提前假设。 -->
- 

## 小队闭环追踪（由小队维护）
- 当前阶段：P0 / P1 / P2 / P3 / P4 / 待人类确认 / 已交接
- 启用成员：
- 知识库最新 PRD 稳定链接：
- Issue metadata 中的 `artifact_requirement_internal_link`：
- 最终 `multica-verification`：PASS / FAIL；证据或评论链接：
- 阻塞型 OP-：无 / <编号与负责人>
- 人类产品范围确认：未确认 / 已确认（确认人、日期：）
- 交接目标：开发小队 / 软件开发小队 / 不适用
```

---

## 为什么这样写

- Issue 先描述问题、用户和结果，避免把未经验证的解决方案直接交给 UI/UE设计师 或开发。
- 输入不要求预选智能体数量；产品总监结合资料和产品影响判断 L1 / L2 / L3。
- 成功指标和已知约束帮助 产品经理 形成可评审、可验收的产品定义。
- 待确认项提前显性化，但正式 OP- 清单仍由 产品经理 在 PRD 中统一维护。
- 闭环追踪字段把 PRD 知识库链接、最终评审、人工确认和开发交接放在同一 Issue，避免“设计完成但没有可消费版本”。

## 常见失败

- 只写“做一个某某页面”，没有说明用户问题和期望结果；
- 把竞品截图当成已确认需求，没有解释适用场景；
- 预先要求所有角色参加，导致简单产品定义承担完整小队成本；
- 隐藏关键约束，让产品设计在评审后被迫整体返工；
- 设计平台有链接，但 Issue 没有最新知识库 PRD 链接或最终评审证据。
