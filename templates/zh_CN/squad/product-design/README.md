# 产品设计小队启动模板

> 面向各种产品功能设计的 Multica 小队：从想法、问题或改进诉求出发，形成经过 产品总监 统一评审的产品定义包。
> **复制、粘贴、运行。**

## 小队定位

这个 启动模板负责产品设计阶段：

```text
想法 / 问题 / 改进诉求
  ↓
产品总监 第一时间派 产品经理
  ↓
产品经理 产品分析与产品定义 / PRD
  ↓
产品总监 判断是否需要继续设计
  ↓
按需派 UI/UE设计师 / 技术架构师（不做中间评审）
  ↓
产品总监 最终统一 评审
  ↓
人类确认 → 产品定义交接包
```

它可以设计新功能、现有功能优化、工作流 / 审批、权限与状态机、数据看板、跨系统协作和多端体验，但不负责代码实现、正式测试、部署或上线。

## 成员

| 逻辑角色 | 复用的 智能体 | 启用方式 |
| --- | --- | --- |
| 产品总监 | `agents/product-leader.md` 或 小队提示词 | 必需；产品分诊、编排、通用门禁、升级 |
| 产品经理 | `agents/product-manager.md` | 必需；产品定义与 PRD |
| UI/UE设计师 | `agents/designer.md` | 涉及页面、交互或多端体验时启用 |
| 技术架构师 | `agents/architect.md` | 涉及跨系统、数据、权限、性能或高成本方案时启用 |

产品总监 是本小队唯一评审者，负责最终统一门禁、返工判定和最终放行；不代替 产品经理、UI/UE设计师 或 技术架构师 产出内容。产品经理 完成后只做是否继续派人的判断，不做中间正式评审。

## 动态编排

| 复杂度 | 判断信号 | 默认组合 |
| --- | --- | --- |
| L1 轻量产品定义 | 单一功能、已有页面小改动或局部优化，边界清楚 | 产品总监 + 产品经理；产出精简变更说明 |
| L2 体验设计 | 新页面、关键交互、多角色流程或多端体验 | L1 + UI/UE设计师 |
| L3 复杂产品 | 跨系统、数据口径、权限状态机、核心流程或高成本约束 | L1 + 按需 UI/UE设计师 和 / 或 技术架构师 |

复杂度和后续成员由 产品总监 在 P0 读取输入与现有资料后决定，但第一个下游必须是 产品经理。已有清晰 PRD / Issue 时仍先交给 产品经理 做轻量复用和增量校验，不重复索要完整字段。L1 只补问题 / 目标、变更范围和验收标准等必要信息；不相关的权限、KPI、状态机和数据口径不作为阻塞项。

## 成本控制

产品设计小队默认采用轻量路径，不会因为成员已经加入小队就全部调用：

| 模式 | 默认调用 | 适用场景 |
| --- | --- | --- |
| L1 轻量 | 产品总监 + 产品经理 | 单一功能、局部优化、已有页面小改 |
| L2 标准 | L1 + UI/UE设计师 | 新页面、关键交互、多角色或多端体验 |
| L3 高风险 | L1 + 按需 UI/UE设计师、技术架构师 | 跨系统、复杂数据 / 权限、核心流程或高成本决策 |

每次派活只传递任务摘要包、稳定产物引用和本次变化，不默认复制完整聊天历史、完整 PRD 或无关产物。L1 只评审本次变化及受影响的 AC-；没有语义变化时复用已有产物和评审结论。返工上限为 L1 一轮、L2 两轮、L3 三轮，超过上限直接升级人类。

## 统一评审

正式评审只在所有需要的产物完成后由 产品总监 统一负责：

1. 产品经理 完成后，产品总监 判断是否还需要 UI/UE设计师 / 技术架构师，不形成中间 PASS / FAIL。
2. 需要其他角色时直接派发，等待所有适用产物完成；不调用其他 业务评审智能体。
3. 汇总全部产物后使用 `multica-verification` 进行一次最终一致性评审，PASS 才交接；FAIL 只退回具体作者，返工后再次回到最终评审。

返工上限按复杂度执行：L1 一轮、L2 两轮、L3 三轮，超过上限仍不通过则升级人类。作者自检不能代替 产品总监 评审。

## 使用的技能

| Skill | 挂载角色 | 用途 |
| --- | --- | --- |
| `multica-verification` | 产品总监 | 通用门禁与跨产物一致性检查 |
| `multica-requirement-analysis` | 产品经理 | 把问题与想法结构化为产品定义 |
| `multica-artifact-req-sync` | 产品经理、UI/UE设计师、技术架构师 | 首次落地及后续更新同一份 PRD 到知识库，并返回最新稳定引用 |
| `multica-artifact-ui-sync` | UI/UE设计师 | 落地 UI / 交互设计 |
| `multica-technical-design` | 技术架构师 | 技术可行性和约束分析 |
| `multica-artifact-design-sync` | 技术架构师 | 落地技术设计 |

具体平台、URL 和凭证仍然只放在对应的 `multica-platform-*` 壳中。

## 5 分钟上手

### 第 1 步：复用智能体

复用现有的 产品经理、UI/UE设计师、技术架构师；产品总监 使用 小队提示词 编排。若工作区需要独立 小队负责人智能体，使用 [`../../agents/product-leader.md`](../../agents/product-leader.md)。

命名遵循 [`docs/zh_CN/naming-conventions.md`](../../../../docs/zh_CN/naming-conventions.md)。

### 第 2 步：挂载 Skill

按上表为各 智能体 挂载 Skill。Skill 按名称引用，不把仓库路径或公司平台配置写进 智能体 提示词。

### 第 3 步：创建小队

把 [`squad.md`](./squad.md) 的代码块复制到 小队提示词，并加入上表中的成员。

### 第 4 步：创建 Issue

把 [`issue.md`](./issue.md) 复制到新 Issue。优先填写问题、目标、变更范围和验收标准；已有外部 PRD 时提供链接和本次变化即可。不要预先指定需要几名 智能体 或写死解决方案。

### 第 5 步：运行

```text
P0 分诊
  → P1 产品经理 产品定义
  → 产品总监 判断是否需要 UI/UE设计师 / 技术架构师
  → 按需完成 UI / 交互设计和 / 或技术可行性，并更新知识库中的同一份 PRD（不做中间评审）
  → P4 产品总监 最终统一评审
  → 人类确认与交接
```

## 产品定义交接包

完成时至少包含：

- 产品目标、用户、范围与非范围；
- 用户故事、功能需求、业务规则和验收标准；
- 权限、状态、字段 / 指标口径；
- 正常、空、异常、无权限等关键状态；
- UI / 交互设计引用（如适用）；
- 技术可行性、依赖与约束引用（如适用）；
- 知识库中最新版本的同一份 PRD 稳定链接；
- 产品总监 对产品定义、UI / 交互和技术方案的最终结论；
- 已关闭和仍待人类决定的 OP-；
- 给开发小队的拆分建议、风险和验证关注点。

只有人类可以确认产品范围并把交接包送入开发。评审 PASS 不代表代码、测试或上线已经完成。

## 什么时候使用

- 从想法、业务问题或用户反馈设计新功能；
- 优化现有流程、页面、权限、状态机或数据看板；
- 需要产品、体验和技术可行性按复杂度组合；
- 希望产品产物经过统一质量评审后再交给开发。

## 什么时候不要使用

- PRD 和设计已经确认，只需要写代码：使用 [`development`](../development/README.md)；
- 需要完整开发、测试和部署：使用 [`software-development-reviewed`](../software-development-reviewed/README.md)；
- 紧急线上故障：使用 [`bug-fix`](../bug-fix/README.md)。

## 为什么有效

- 产品功能先由 产品经理 定义，不让 UI/UE设计师 或工程师反向猜业务规则。
- UI 和技术可行性按需启用；只启用一个角色时直接执行，两者都启用时按 UI/UE设计师 → 技术架构师 顺序补写同一份 PRD，不把所有产品任务都做成大流程。
- 产品总监 统一检查各产物与验收标准的一致性，减少 业务评审智能体 和重复上下文。
- 最终交付的是开发小队可消费的统一产品定义包，而不是互相冲突的 PRD、设计稿和技术意见。

## 常见失败

- 一开始就画页面，没有先定义用户问题、范围和业务规则；
- 产品经理、UI/UE设计师 和 技术架构师 同时修改同一份产品口径；
- UI 或技术方案变化后继续沿用过期的评审结论；
- 设计完成后只回传设计平台链接，没有把更新后的 PRD 回写知识库；
- OP- 未关闭就把模糊需求交给开发。
