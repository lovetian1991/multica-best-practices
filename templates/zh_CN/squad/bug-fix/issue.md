# Issue 模板

> 复制到新 Issue，填写后交给小队。

```markdown
# Bug

## Issue 来源（必填，二选一）
<!-- 选「外部系统链接」时，仅填链接 + 复现摘要 + 影响端，其余章节跳到「参考资料」引用 KEY；全量细节在 Jira/Tapd 等系统中 -->
- [ ] 外部系统链接（轻量）：仅填「链接 / 一句话复现摘要 / 影响端」
      - 链接：<ISSUE_URL>
      - 摘要：<!-- 一句话说明现象 -->
- [ ] 全量自包含（默认）：本 Issue 即为需求，完整填写以下所有章节

## 复现步骤
1.
2.
3.

## 期望行为
<!-- 应该发生什么 -->

## 实际行为
<!-- 实际发生了什么 -->

## 影响范围
- 影响端（勾选，缺失即不派角色）：
  - [ ] 前端
  - [ ] 后端
- 影响的用户 / 模块 / 版本：

## 根因假设
<!-- 如果已知，写在这里 -->

## 修复要求
- [ ] 定位根因
- [ ] 最小范围修复
- [ ] 回归测试（或说明无法自动化的原因）

## 验收标准
- [ ] 按复现步骤不再出现该问题
- [ ] 既有行为不回归
- [ ]

## 参考资料
<!-- 日志、截图、错误信息、相关代码位置 -->
```

---

## 为什么这么写

Bug Issue 的第一要务是「可复现」。复现步骤 + 期望/实际行为三段写清，实现者才能不靠猜直接定位根因。

## 常见失败

- **只有一句话描述、没有复现步骤**：实现者只能靠猜改代码，根因永远定位不到，修了这里坏那里。
- **复现步骤依赖环境细节却没写**（版本、数据、登录态）：别人复现不出，门禁无法判 PASS。
- **期望/实际行为缺失**：改完无法判断"修好了"，验收标准形同虚设。
- **直接给"解决方案"代替根因**：本模板要的是根因假设，不是让人在 Issue 里写补丁；没根因的修复大概率回潮。
- **回归验证被跳过**：只改代码不加回归用例，同样的触发条件下次还会再爆。
