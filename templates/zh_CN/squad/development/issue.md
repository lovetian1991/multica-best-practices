# Issue 模板

> 复制到新 Issue，填写后交给开发小队。

```markdown
# 开发任务

## Issue 来源（必填，二选一）
- [ ] 外部系统链接（轻量）
      - 链接：https://jira.example.com/browse/<ISSUE-KEY>
      - 摘要：<!-- 一句话说明要开发什么 -->
- [ ] 全量自包含（默认）

## 背景
<!-- 为什么要做这件事？ -->

## 目标
<!-- 这次开发需要解决什么问题？ -->

## 范围
<!-- 描述要改变的业务或技术范围。具体涉及前端、后端、架构和 API 由研发总监在 T0 分诊确认。 -->
- 要改变什么：
- 相关模块 / 服务：

## 非目标
<!-- 明确这次不做什么，避免实现者扩大范围。 -->
- 

## 验收标准（必须可测试）
- [ ] 
- [ ] 
- [ ] 

## 约束与参考
<!-- 现有接口、兼容性要求、代码位置、设计或外部文档链接。 -->

## 备注
<!-- 其他需要研发总监、技术架构师或工程师知道的信息。 -->
```

---

## 为什么这样写

- Issue 提供目标、范围、非目标和验收标准，研发总监再结合现有代码判断复杂度和参与成员。
- 不在 Issue 中固定填写“必须启动前端 / 后端 / 架构师”，避免简单任务被迫走完整流程。
- 验收标准必须可测试，否则研发总监无法执行开发门禁。
- 技术方案、API 契约、变更文件和验证证据由开发小队在运行中产生，不提前伪造。

## 常见失败

- 只写“请把功能做完”，没有目标或验收标准；
- 把实现方案直接写死在 Issue，限制 技术架构师 和工程师检查现有代码；
- 把复杂度和智能体数量当成需求内容，由 Issue 创建者替研发总监决定；
- 没有写非目标，导致开发范围不断扩大。
