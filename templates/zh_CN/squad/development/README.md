# 开发小队启动模板

> 面向软件开发的轻量 Multica 小队：研发总监动态编排技术架构师、前端开发专家、后台开发专家。
> **复制、粘贴、运行。**

## 小队定位

这个启动模板专注于开发阶段：

```text
Issue
  ↓
研发总监判断复杂度与范围
  ↓
按需启用 技术架构师 / 前端开发专家 / 后台开发专家
  ↓
实现与开发验证
  ↓
开发交接包
```

它不会默认拉入产品、设计、测试或部署运维角色。开发交接完成后，可以把交接包交给现有的 `software-development` 流程、测试小队或部署运维小队。

## 成员

| 逻辑角色 | 复用的 智能体 | 主要职责 |
| --- | --- | --- |
| 研发总监 | `agents/development-leader.md` 或 小队提示词 | 分诊、动态组队、协调、门禁、升级 |
| 技术架构师 | `agents/architect.md` | 技术分析与架构设计，按复杂度启用 |
| 前端开发专家 | `agents/frontend-developer.md` | 前端实现与验证，按范围启用 |
| 后台开发专家 | `agents/backend-developer.md` | 后端实现、API 契约与验证，按范围启用 |

研发总监是必需的逻辑角色，但不一定需要单独创建智能体。Multica 若只向研发总监注入小队提示词，直接使用 `squad.md` 即可；已有独立研发总监智能体时，使用 [`../../agents/development-leader.md`](../../agents/development-leader.md)。

## 动态编排

| 复杂度 | 判断信号 | 默认组合 |
| --- | --- | --- |
| L1 简单 | 单端、局部模块、无公共契约或架构变化 | 研发总监 + 一个相关工程师 |
| L2 中等 | 多模块、前后端联动、公共 API 变化 | 研发总监 + 相关工程师，技术架构师按需加入 |
| L3 高风险 | 核心架构、数据迁移、安全、性能、跨服务或重大兼容性 | 研发总监 + 技术架构师 + 相关工程师 |

复杂度不是 Issue 填写者预先指定的固定人数，而是研发总监在 T0 读取需求和代码后形成的判断。执行中发现风险变化时，研发总监可以增派或结束成员，并记录原因。

## 使用的技能

| Skill | 挂载角色 | 用途 |
| --- | --- | --- |
| `multica-verification` | 研发总监 | 独立复跑验证并执行开发门禁 |
| `multica-requirement-analysis` | 研发总监 / 技术架构师 | 需求和范围结构化，按需使用 |
| `multica-technical-design` | 技术架构师 | 技术方案和验证方式 |
| `multica-implementation` | 前端开发专家 / 后台开发专家 | 开发实现方法 |
| `multica-artifact-design-sync` | 技术架构师 | 技术设计产物落地，按需使用 |
| `multica-artifact-api-sync` | 后台开发专家 | API 契约落地，按需使用 |

生产环境 URL、凭证和具体平台仍然只放在对应的 `multica-platform-*` 壳中。

## 5 分钟上手

### 第 1 步：创建或复用智能体

复用以下现有 智能体 提示词；本启动模板 使用专属 `研发总监`：

```text
研发总监
技术架构师
前端开发专家
后台开发专家
```

研发总监使用小队提示词编排；如果 Multica 工作区使用独立研发总监智能体，则复制 [`../../agents/development-leader.md`](../../agents/development-leader.md)。

命名遵循 [`docs/zh_CN/naming-conventions.md`](../../../../docs/zh_CN/naming-conventions.md)：

```text
技术架构师-<project>-<member-id>
前端开发专家-<project>-<member-id>
后台开发专家-<project>-<member-id>
```

### 第 2 步：挂载技能

创建或复用上表中的 Skill，并按“挂载角色”分配。Skill 按名称引用，不要把仓库路径写进智能体提示词。

### 第 3 步：创建小队

创建小队，把 [`squad.md`](./squad.md) 的代码块复制到小队提示词。

### 第 4 步：创建 Issue

把 [`issue.md`](./issue.md) 复制到新 Issue，填写目标、范围和可测试的验收标准。不要在 Issue 中硬编码本次必须启动几名智能体；由研发总监分诊。

### 第 5 步：运行

把 Issue 分配给小队。研发总监会先完成 T0 分诊，再按需派发：

```text
T0 分诊 → T1 技术准备（按需）→ T2 API 契约（按需）→ T3 实现 → T4 开发交接
```

## 开发交接完成的定义

开发小队完成交接时，必须有：

- 本次复杂度等级和实际参与成员；
- 变更文件清单；
- 验收标准逐条对应；
- 技术设计或 API 契约引用（如适用）；
- 实际验证命令和结果；
- 已知限制、风险和未覆盖范围；
- 测试与部署运维的后续注意事项。

这只代表开发阶段完成。测试通过、部署成功和业务验收仍由对应小队或人类完成。

## 什么时候使用

- 已经有明确需求或 Bug，需要专注完成代码开发；
- 想让前后端按任务范围单独或并行工作；
- 希望由研发总监根据复杂度控制上下文和智能体数量；
- 需要把开发阶段和测试、部署运维拆成可组合的小队。

## 什么时候不要使用

- 需求目标和验收标准还没有形成；
- 需要产品探索、用户研究或 UI 设计；
- 需要独立测试验收或生产发布；
- 任务是紧急线上故障，优先使用 [`bug-fix`](../bug-fix/README.md)。

## 为什么有效

这个启动模板把小队作为开发能力池的编排配置，把复杂度判断放到研发总监的 T0 阶段。这样同一个开发小队既可以处理单端小任务，也可以处理完整的前后端功能；人员按需启用，产物按需产生，后续仍能交给其他小队。

## 常见失败

- 把四个成员当成每次都必须同时运行的固定班底；
- 让工程师自己决定产品范围或给自己的实现盖章；
- 没有先读代码就判断任务简单；
- 跳过 API 契约后让前端猜接口；
- 只返回口头完成结论，不提供可复现证据。
