# 需求（PRD）专业评审（产品评审）

本 skill 提供对 **PRD / 需求产物**的结构化专业评审框架。调用方为 `产品评审`，评审对象为 `产品经理` 经 `multica-artifact-req-sync` 回传的 PRD 链接。

## 什么时候用

- 产品评审收到对应小队负责人派发的「评审 PRD」任务时。
- PRD 修改后进入复审轮次时（对照上一轮修改清单逐条核对）。

## 评审维度（逐项给结论）

1. **范围清晰**：边界清楚、无歧义、可拆分任务；无隐含范围。
2. **目标明确**：解决的问题可度量，不含模糊表述。
3. **验收可测**：每条 AC- 都能被客观验证，无「体验好」类模糊标准。
4. **约束完备**：权限、异常、合规、依赖方、数据口径是否列出。
5. **待确认项**：OP- 是否完整列出，并正确区分为阻塞项或非阻塞跟进项。只有影响当前范围、业务规则、权限 / 数据口径、AC- 或安全合规的 OP- 才能作为阻塞项。

## OP- 判定规则

- **阻塞项**：未解决会导致当前范围、关键业务规则、权限 / 数据口径、AC- 或安全合规无法判断、无法验收，或会让下游设计 / 开发产生实质性返工。阻塞项未关闭时可以 FAIL。
- **非阻塞跟进项**：普通偏好、文案细节、实现选择、可后补资料，或不影响当前范围与验收的内容。必须记录负责人和后续时点，但不单独导致 FAIL，也不阻断已具备条件的下游工作。
- 产品评审 不得因为“OP- 未全部关闭”而整体 FAIL；应检查分类是否合理，并把非阻塞跟进项单独列出。

## 输出格式

```text
【PRD 评审】<PRD 链接>
结论：PASS / FAIL
阻断项（FAIL 时必填，每项含 理由 / 涉及点 / 修改方向）：
- ...
非阻塞跟进项（不阻断 PASS，含负责人 / 后续时点，如适用）：
- ...
与上一轮修改清单核对（复审时）：已解决 X 项 / 未解决 Y 项
轮次：第 N / 3 轮
```

结论与修改清单**汇报给对应小队负责人**，不自行改 PRD、不自行通知产品经理。

## 边界

- 只评 PRD/需求，不评设计、代码、测试用例、UI。
- 不替代对应小队负责人的通用门禁（`multica-verification` skill）。
- 技术可行性交 架构评审，你只管需求层质量。
- 第 3 轮仍 FAIL → 标注「升级人类」，交对应小队负责人处理，停止循环。
